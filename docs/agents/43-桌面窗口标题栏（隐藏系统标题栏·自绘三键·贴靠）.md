## 43. 桌面窗口标题栏（隐藏系统标题栏 · 自绘三键 · 贴靠 / 缩放，2026-10-09 立）

用户原话：「我希望把系统标题栏隐藏，然后让我们的顶部标题栏支持三键（最小化/最大化/关闭）。
然后让我们的顶部标题栏支持系统标题栏的各种特性。并且设置里可以调关于此标题栏的两项：
① 交换左侧应用 logo 与右侧三键的位置，变成左侧三键，右侧 logo；② 允许选择 win 风格三键
与 mac 风格」。

三轮 ask 拍板：① 标题栏**全局一条**，首页品牌栏并入它（宫格视图的设置+头像挪进标题栏
右侧、三键左边；侧栏视图仍在侧栏底部固定区）；② mac 风格默认三键靠左（mac 惯例），
仍可用第一项设置换到右侧；③ **全都要** —— 拖动、双击最大化/还原、右键系统菜单、边缘
缩放、Aero 贴靠、**Win11 贴靠布局（悬停最大化按钮弹贴靠面板）**。

### 43.1 三层分工（改之前先认清谁负责什么）

| 层 | 文件 | 职责 |
|---|---|---|
| 原生窗口 | `windows/runner/window_chrome.{h,cpp}` | 藏系统标题栏（`WM_NCCALCSIZE`）+ 命中测试（`WM_NCHITTEST`）+ 三键动作 + 把窗口状态推给 Dart |
| Dart 地基件 | `lib/core/window/window_chrome.dart` | 平台通道、窗口状态、命中区上报；`lib/core/window/window_title_bar_actions.dart` = 页面动作插槽 |
| Dart 界面 | `lib/design/window_title_bar.dart` + `lib/features/settings/data/window_bar_prefs.dart` | 画（品牌 / 三键 / 页面动作）、量（每帧把几何上报）、两项偏好的存取 |

**一句话口径：Dart 画与量，原生判命中。** Dart 每帧把「栏高 + 三键矩形 + 页面动作矩形」
（**逻辑像素**）经通道 `smarter_jxufe/window_chrome` 推给原生；原生按窗口 DPI 换算成物理
像素，在 `WM_NCHITTEST` 里返回非客户区命中码 —— 于是所有窗口行为都是系统的，Dart 侧
一个手势都不用写。

### 43.2 原生侧五个关键点（每一条都踩过坑）

1. **只藏标题栏，不藏边框 —— 而且是「真的」系统边框**（2026-10-09 用户二轮：
   「我怎么觉得你没用系统原生边框呢」→ 改按 `window_manager` 0.4.3 `TitleBarStyle.hidden`
   的几何重做，见 43.7）：
   - `WM_NCCALCSIZE`（`wParam=TRUE`，非最大化）：`top += IsWindows11OrGreater() ? 0 : 1`
     —— **顶部不留**，自绘标题栏贴住窗口顶边（与原生 caption 位置一致；Win10 那 +1 是
     window_manager 踩出来的「顶边一条白线」）；
     **左 / 右 / 底各收掉 `SM_CXSIZEFRAME + SM_CXPADDEDBORDER`** → 那圈是**真非客户区**：
     DWM 画边框 / 圆角 / 阴影，缩放热区由系统自己提供。
   - 最大化：按**显示器工作区**把客户区扩回来（`MonitorFromRect` +
     `GetMonitorInfo().rcWork`，window_manager 的 `adjustNCCALCSIZE` 同款公式），
     否则内容会被挤出屏幕 / 压到任务栏下面。
   - `WM_NCACTIVATE` → **`return 1`**（window_manager 同款）：自绘标题栏时不让系统重画
     非客户区，否则激活 / 失活那一下会把栏背景擦成系统 caption 的颜色。
   - ⚠ **`SWP_FRAMECHANGED` 必须显式喊一次**：窗口创建时的第一条 `WM_NCCALCSIZE` 早于
     `WindowChrome` 对象存在（那时 `FlutterWindow::chrome_` 还是 nullptr），系统按「有标题栏」
     算了一次客户区；不重算 → 客户区比窗口小 **22×56**（系统标题栏还在，应用又在它下面画了
     一条自绘栏）。而且这次重算**必须在 `chrome_ = std::make_unique<...>` 赋值之后**调
     （放在构造函数里等于没调 —— 那时消息入口的 `if (chrome_)` 还是 false）。
   - ⚠ **`WM_NCHITTEST` 对边框圈必须回「不归我判」（`std::nullopt`）**：旧版对客户区外的点
     一律回 `HTCLIENT` → **整个边框拖不动**（2026-10-09 探针实测：右边缘拖拽 1600 → 1600
     毫无反应）。只有把那些点交回 `DefWindowProc`，系统才给得出
     `HTLEFT/HTRIGHT/HTBOTTOM` 与四角。**顶部那一条**因为 `top += 0` 落在客户区里，
     另由 `TopBorderHit()` 补回 `HTTOP`/`HTTOPLEFT`/`HTTOPRIGHT`（比 window_manager 多这一条
     —— 它那套顶边是不能拖拽缩放的）。
2. **子窗口会把命中测试吃掉**：`FlutterViewController` 的视图是铺满客户区的子窗口，而
   `WM_NCHITTEST` 是发给**光标下最深的那个窗口**的 —— 顶层窗口一个都收不到。做法 =
   `SetWindowSubclass` 子类化 Flutter 视图，对**标题栏带**（含顶边那条缩放区）返回
   `HTTRANSPARENT`（同线程内系统会继续问父窗口），其余 `DefSubclassProc` 原样交给引擎 =
   Flutter 正常收鼠标事件。参考：吕毅《当无边框窗口被子窗口遮挡导致难以调节窗口大小时…》。
   （左/右/底的边框圈不用在这里让路 —— 子窗口的矩形本来就不覆盖它们。）
3. **三键回非客户区命中码**：`HTMINBUTTON` / `HTMAXBUTTON` / `HTCLOSE`；标题栏空白处回
   `HTCAPTION`（白送拖动、双击最大化/还原、右键系统菜单、Aero 贴靠）。
   `HTMAXBUTTON` 是 **Win11 贴靠布局的官方契约**（MS Learn《Support snap layouts for
   desktop apps on Windows 11》）。三键的**动作自己做**（`WM_NCLBUTTONUP` 落在同一键上才
   触发，滑出去再松手 = 取消；`SC_MINIMIZE` / `SC_MAXIMIZE` / `SC_RESTORE` / `SC_CLOSE`
   用 `PostMessage` 发），这样 Dart 才能拿到按下/抬起态去画高亮。
4. **尺子按窗口 DPI 取**：`GetSystemMetricsForDpi(SM_CXSIZEFRAME/SM_CXPADDEDBORDER, dpi)`。
   ⚠ 本进程是 PerMonitorV2，`GetSystemMetrics` 返回的**已经**是按（系统）DPI 缩放过、再乘
   一次 `GetDpiForWindow/96` → 150% 缩放下缩放边框厚成 **24px**，标题栏带下半截被判成缩放区
   → 「三键点不动、点标题栏变成拉高度」（实测就是这个症状）。
5. **Windows 11 判定走 `RtlGetVersion`**（ntdll，动态取导出）：本进程带 manifest，
   `GetVersionEx` 会按 manifest 谎报版本；拿不到就按 Win10 处理（多留 1px，保守）。

### 43.3 Dart 侧的五个口径

- **只有 Windows 画**：`windowTitleBarSupported(context)` 判 `Theme.platform`（与
  `homeDesktopPlatform` 同口径，测试里换主题就能按平台跑）；通道侧另有
  `windowChromeSupported`（判 `defaultTargetPlatform`）。非 Windows 原样透传
  （系统标题栏还在，再画一条只会凭空多一条空栏）。
- **必须原生先应答（`nativeReady`）**：判据 = `getWindowState` 有回值，或收到过任何原生
  事件。**旧 exe + 新 Dart 包**这种版本错配下通道根本不存在，照画就会画出一条三键点不动的
  假标题栏（而系统标题栏也还在 → 屏幕上两条）→ 没应答就整条 chrome 不画，退回只有系统
  标题栏的旧观感。守卫 = 测试里「原生没应答 → 不画也不上报」「原生推来第一个事件也算握手」。
- ⚠ **标题栏必须自带 `Material` + `Overlay`（2026-10-09 实测 · 缺一个整个应用起不来）**：
  页面动作区挂的是 `IconButton`（`Tooltip` 在 **build 期**就要 `Overlay` 祖先）与
  `AccountAvatar`（`InkWell` 要 `Material` 祖先），而标题栏是 Navigator 的**兄弟** ——
  navigator 那两样都不在它的祖先链上 → 首帧抛
  `No Overlay widget found. Tooltip widgets require an Overlay widget ancestor`。
  **后果比普通异常重**：Windows runner 是「首帧之后才 `ShowWindow`」→ 进程活着、
  `MainWindowHandle = 0`、**永远没有窗口**（看着像卡死）。修法 = `SizedBox(height: …)`
  钉死高度 + `Material(type: transparency)` + 内联 `Overlay`（高度**不能用
  `IntrinsicHeight` 去问**：`Overlay` 在高度方向没有上界，会算出天文数字 →
  `RenderFlex overflowed by 99044 pixels`）。守卫 = 测试里「标题栏自带 Material + Overlay」。
- **几何按「量到的」上报**：`_TitleBarRegion`（`RenderProxyBox`）在 **paint** 里
  `localToGlobal` 记录矩形（不触发重建），post-frame 时统一推给控制器；控制器**按值去重**
  （每帧都推会白刷通道）。量不到就上报 `enabled: false` —— 宁可少一个拖动区，也不要让一条
  看不见的带子把点击吃掉。
  ⚠ **每个区域必须带 key**：不带 key 时 `Row` 的 children 按位置复用，页面动作一出现/消失
  后面三键的 element 整体错位一格，末位卸载时会把**别人的** token 从表里删掉
  （实测：动作收回后 `interactive` 变成 null、整条栏退回「没有标题栏」）。
- **三键是纯视觉**：点击由原生处理，悬停/按下/失焦/最大化由原生**推**（`windowState` /
  `titleBarPointer`）。`WindowChromeSnapshot.isHovered/isPressed` 已经把「失焦不给高亮」
  这条原生语义收进来了。
- **页面动作走插槽**：`windowTitleBarActionsProvider`（`ChangeNotifier`）让页面把自己的
  动作交给全局标题栏。⚠ 标题栏是页面的**祖先**（挂在 `MaterialApp.builder` 上），页面在
  build 里改它 = 「build 期间 markNeedsBuild」直接报错 → 首页用 **post-frame** 发布
  （`_queueTitleBarActions`），代价是最多晚一帧。⚠ 标题栏拿到的 `context` 在 Navigator
  **之外**，`Navigator.of(context)` 找不到路由 —— 动作里的导航一律走页面自己的
  `context` + `mounted` 守卫。

### 43.4 两项设置（外观节）

`lib/features/settings/data/window_bar_prefs.dart`：Hive box `windowBarPrefs`（key
`buttonsStyle` / `swapSides`），`ChangeNotifier` + `ChangeNotifierProvider`，`main()` 里
**预热**（标题栏是第一帧就画的 chrome，异步读盘会让它先按默认值画一次再跳）。

- **位置**：`windowButtonsOnLeft({style, swapSides})` —— Windows 风格默认不交换（logo 左 /
  三键右）；mac 风格默认交换（三键在左 = mac 惯例），`swapSides` 仍能把它换回右侧。
- **风格**：`WindowButtonsStyle.windows`（46×栏高的矩形按钮，悬停 `onSurface` 8% 底、
  关闭键悬停 `#C42B1C` 白字 —— Win11 语义，登记在 `WindowChromeTone`；这两个值照
   vshell 的 `--vscode-list-hoverBackground` 与 `#c42b1c`）/ `.mac`
  （三个 12px 圆点、槽宽 20，`#FF5F57`/`#FEBC2E`/`#28C840`，悬停任意一个三个都显符号，
  失焦整组转灰 `#C6C6C6`）。mac 在三键左侧时按 macOS 惯例排成「关闭/最小化/最大化」。
- **三键图标 = codicon 字体**（`WindowTitleBarGlyph` + `Codicons`）+ 字号
  `kWindowTitleBarGlyphSize = 16`（墨迹约 10px，与原生 caption 图标同尺寸）。
  用户 2026-10-09 二轮原话：「win 风格三键的 icon 也和原生不一样，我希望你直接去看 vshell
  代码」→ vshell 的就是 `codicon-chrome-minimize/maximize/restore/close`
  （`\eaba`/`\eab9`/`\eabb`/`\eab8`），CSS 里 `font-size: 14px`、按钮 44 宽满栏高。
  **做法**：把 `@vscode/codicons`（MIT）的字体**子集出这四个字形**（147 KB → **1.2 KB**，
  `assets/fonts/codicon-titlebar.ttf`，子集命令写在 `pubspec.yaml` 的 `codicon` family
  注释里），`IconData` 直接引码点。**不许退回自绘线框**（旧版就是被用户指出不一致的那版，
  守卫会拦）。mac 圆点里的小符号仍是自绘（macOS 那套不是 codicon）。
- **mac 三键整组的四周留白**（用户 2026-10-09 四轮原话：「mac 风格的三键距离窗口左右边缘
  太近，我希望 mac 三键作为一个整体，其距离标题栏上下边距与侧边边距要一致」）：
  判据取**圆点墨迹**、按**栏内实际可画高度**算 —— 栏高 40 里底部 1px 是分隔线
  —— ⚠ 那根**分隔线已于 2026-10-09 六轮按用户要求撤掉**（「标题栏底部不要显示那根框线，
  从而让标题栏可以和侧边栏视觉上连续」；顶栏色与侧栏底色本来就同值，深色都是 `#1A1A1A`）
  → 子件拿到整 40，圆点竖直居中距上边 `(40 − 12) / 2 = **14**`；侧边对齐这个数，整组外侧
  再补 `kWindowTitleBarMacClusterInset` = 14 − (20 − 12)/2 = **10**（槽内那半个空隙已在里面）。
  ⚠ **只有 Win 风格贴边**（原生 caption 的观感，按钮顶到栏右缘）；mac 不贴边。
  ⚠ 外侧留白用 `AnimatedPadding` 走同一份动画（0 ↔ 10），换风格时也一起补间。
  ⚠ 槽（命中区）跟着整组一起移动、**宽度不变**（不能靠挤窄槽来留白，否则点击区缩水）。
  实测（`bar_idle.png` 逐像素量，150% 缩放、mac 在左）：圆点墨迹距**客户区**左边
  **14.0** 逻辑像素、距上边 **14.0** —— 两条一致 ✓（改前侧边只有 4 + 槽内空隙）。
  守卫 = 「整组留白：圆点距侧边 = 距栏上下边」「换到右侧时留白贴的是右边（同样一致）」
  「三个圆点槽靠左…」三例（后者已改成从整组留白之后起排）。
- 设置卡 `SettingsWindowBarCard`（`settings_cards_window.dart`）挂在外观节第二张；
  **非 Windows 整卡不画**（那边没有窗口 chrome）。
- **两项的切换都是动画的**（用户 2026-10-09 三轮：「我希望为两个设置项的切换时，添加动画」）：

  | 变化 | 做法 | 时长/曲线 |
  |---|---|---|
  | 换位置 | 品牌组与「三键 + 动作」组各挂一个 `AnimatedAlign`，**反向对滑**（`Alignment.centerLeft ↔ centerRight`） | `kWindowTitleBarSwitchDuration` = 280ms / `easeOutCubic` |
  | 换风格 | 槽宽 46 ↔ 20 走 `AnimatedContainer`（方键「收成」圆点）；键内部用 `TweenAnimationBuilder<double>` 把同一份 t 喂给两层：**矩形高亮 + codicon 字形淡出**、**圆点淡入 + 0.55→1 放大** | 同上 |
  | mac 重排 | mac 在左侧时顺序是「关闭/最小化/最大化」→ 三枚各自 `AnimatedPositioned` 让位 | 同上 |

  ⚠ **每枚按钮必须有稳定 key**（`ValueKey<WindowTitleBarButton>` 在 `AnimatedPositioned` 上、
  按钮自己带 `Key('windowButton-…')`）：不带 key 时 `Stack` 的 children 按位置复用，
  换风格那一帧「最小化」直接变成「关闭」的 element —— 位置是瞬移不是动画。
  ⚠ **形变 ≠ 换树**：不要在风格之间 `AnimatedSwitcher`（半路会出现「两套都满不透明」的
  重影）；同一个 t 驱动两层的透明度才是干净的交叉淡入淡出（守卫：中途必须有一层
  0.05 < opacity < 0.95）。

  ⚠ ⚠ **隐式动画不重建 State → 必须由测量件补上报（真机实测踩过，这条最隐蔽）**：
  `AnimatedAlign` / `AnimatedContainer` / `AnimatedPositioned` 只驱动 RenderObject，
  **不会**重建 `WindowTitleBar`；而当时的几何上报只挂在 `State.build` 里 → 整个动画期间
  （以及动画结束之后）原生拿到的还是**旧矩形**：按钮已经滑到左边了，原生还以为在右边
  → **点新位置没反应、点旧位置触发关闭/最大化**。修法 = `_TitleBarRegion` 在 `paint`
  里发现矩形变了就回调 `onMeasured`（= `_queueLayoutSync`，只排 post-frame 回调、不触发
  重建），由它补一次上报。守卫 = 「动画期间几何变了就必须重新上报」+「最后一次上报 =
  动画后的位置」两例；真机日志可见 280ms 内连发 8 次 `setTitleBarLayout`。

### 43.5 实测台账（2026-10-09 · 本机 150% 缩放 · 原生边框版）

探针都在 `.probe/`（不入库）：`win_chrome_verify.ps1`（客观验收）、
`win_chrome_probe.ps1`（鼠标驱动的端到端）、`win_chrome_visual_probe.ps1`（悬停/贴靠/最大化视觉）。

| 验收项 | 判据 | 实测 |
|---|---|---|
| 系统标题栏摘掉、**原生边框留着** | `GetWindowRect` vs `GetClientRect` | 窗口 1920×1080 / 客户区 **1898×1069 → 差 22×11**（左/右各 11、底部 11、**顶部 0**；占满整窗是旧版） |
| 边框还在 | `GWL_STYLE` 位 | `WS_CAPTION` / `WS_THICKFRAME` / `WS_SYSMENU` / `WS_MINIMIZEBOX` / `WS_MAXIMIZEBOX` 全 True |
| 拖动 | 鼠标拖动标题栏带 | 位移 = 鼠标位移（+120/+80） |
| 双击标题栏 | `IsZoomed` | True（再双击 → False） |
| 边缘缩放 | 拖右边缘 | 宽度 1600 → **1720**（+120；由系统在真边框上完成，我们一行 HitTest 都不写） |
| 三键命中区 | 原生 trace | `layout cx=1200 band=60.0 scale=1.50 close=[1131,1200]`，逐点命中 `HTCLOSE`/`HTMAXBUTTON`/`HTMINBUTTON` |
| 三键动作 | `IsZoomed` / 进程退出 | 最大化 True → 再点 False；最小化 `IsIconic=True`；关闭 = 进程退出 |
| 悬停高亮 | 截图 | 关闭键整键变红 + 白 ✕（原生 `WM_NCMOUSEMOVE` → 通道 → Dart） |
| **Win11 贴靠布局** | 截图 | 悬停最大化键弹出贴靠面板（两个/三个/四个窗口的版式）✓ |
| 三键图标 | 截图 | **codicon** 字形（— / □ / ❐ / ✕），与 vshell 同一套 |
| 原生边框 | 截图（连窗口外的 12px 一起抓） | 圆角 + 细边框在，内容从边框内侧开始 |
| 窄窗口 | 320 宽视口 | 品牌只留 logo（舍应用名），三键仍画满 46 并照常上报，无 Row 溢出 |

### 43.6 与「vshell」那套实现的关系（用户 2026-10-09 提供的对照，二轮已按它重做）

vshell（Flutter + WebView2）用 `window_manager` 的 `setTitleBarStyle(TitleBarStyle.hidden,
windowButtonVisibility: false)` 藏标题栏、网页自绘三键（codicon）、`startDrag()`/`toggleMax()`
走桥。**读 `window_manager-0.4.3` 源码后的确切结论**（用户要求「直接去看 vshell 代码」）：

| 做法 | window_manager / vshell | 本仓 |
|---|---|---|
| 藏标题栏 | `WM_NCCALCSIZE` 里改 `rgrc[0]`（**不动 window style**） | 同 |
| 边框 | 左/右/底各留 8px **真非客户区**（顶边 0） | 同（厚度按 DPI 取而不是写死 8） |
| 最大化 | 按显示器工作区扩回客户区 | 同 |
| 非客户区重画 | `WM_NCACTIVATE` → `return 1` | 同 |
| 拖动 / 双击 | 网页 `mousedown`/`dblclick` → `startDragging()` / `toggleMax()` | **`HTCAPTION`**：拖动、双击最大化/还原、右键系统菜单、Aero 贴靠全是系统的（少一条 JS→桥→原生的往返） |
| 缩放 | 靠那圈非客户区 | 同（+ 顶边那条 `TopBorderHit` 补回 —— window_manager 顶边不能缩放） |
| 三键 | 网页按钮 + `minimize()`/`toggleMax()`/`close()` | **`HTMINBUTTON`/`HTMAXBUTTON`/`HTCLOSE`** → 白送 **Win11 贴靠布局面板**（vshell 那条路线没有） |
| 三键图标 | codicon 字体（44 宽满栏高、14px） | **同一套 codicon**（子集字体 1.2 KB；按钮 46 宽满栏高、16px） |
| 依赖 | `window_manager` 插件 | 零新增依赖（原生自己 660 行 C++） |






### 43.4.1 三处收尾修补（2026-10-09 · 用户连续报的三个问题）

1. **按不动**：「顶部标题栏加的三个按钮都按不动」—— 根因是 `_syncLayout()` 上报原生时
   `interactive` 只带了 `actions` 一个矩形，新加的两簇（侧栏开关 `leading`、路由历史
   `history`）从没进名单，原生把点击当 `HTCAPTION`（拖窗口）吃掉。**判据：凡是标题栏里要
   响应点击的簇，都必须进 `interactive` 名单**（名单在 `_syncLayout()` 里逐个列出，漏一个
   = 那一簇点不动）。守卫 = `window_title_bar_test.dart` 的两条几何用例（现在断言名单里
   ≥2 条：路由历史恒在 + 页面动作那一簇）。
2. **悬浮被裁**：「这几个按钮的悬浮显示都被标题栏边界裁切了」—— `Tooltip` 是以 **overlay
   entry** 的形式画出来的，而 `AppWindowChrome` 原来把 `Overlay` 套在**那 40 高的带子**里
   → 气泡被 Overlay 的边界裁掉。**修法：`Overlay` 罩住整块 chrome（带子 + 页面内容）**，
   `Material` 仍只包带子、带子高度仍显式钉死（`kWindowTitleBarHeight`）。守卫 =
   `window_title_bar_test.dart` 的「整块 chrome 的 Overlay」一例。
3. **侧栏开关搬家**：展开 / 收起从侧栏挪到标题栏品牌组最前面 —— 见 §44.1.13。

## 43.5 排布模型：四区 × 四槽（2026-10-10 重构）

**起因**：标题栏原先是单文件 1146 行、7 个类挤一起，排布规则散在 130 行的 `build` 里用
`if (narrow && …)` / `isMac && buttonsOnLeft ? … : …` 拼出来 —— 于是出了两个只有点开界面
才发现的 bug ✗：① **mac 风格 + 交换三键 → 三键整个不可见**（判据把「风格」和「在哪一侧」
混成一个，方键字形透明度 `1 - macReveal` = 0）；② **窄屏下三键跟着动作簇漂到左边**
（两件事共用一个 `AnimatedAlign`）。

### 43.5.1 四区的定义

| 区 | 装什么 | 占位规则 |
|---|---|---|
| `controls` | 窗口三键 | **只**由「三键左右互换」决定 —— **任何宽度都不动**（用户 2026-10-10：「我希望右上角三键位置不要漂移」） |
| `actions` | 页面发布的动作簇（头像 + 设置） | 宽屏：与三键**同侧紧挨**；窄屏：三键**对侧**（并捎带 `center`）。未发布 → `hidden` |
| `center` | 侧栏开关 + 路由历史 | 宽屏恒 `center`（用户 2026-10-09：「都要放到标题栏中间」）；**窄屏并入 `actions`**（用户 2026-10-10） |
| `brand` | logo + 应用名 | 宽屏：三键对侧；**窄屏 `hidden`**（用户 2026-10-10：「brand 在窄屏不显示」） |

槽位三档 + 隐藏：`TitleBarSlot{left, center, right, hidden}`。

### 43.5.2 阈值 = `Breakpoints.narrow`(600)

用户 2026-10-10：「我希望降低窄屏阈值」—— 顶栏满配约 450px（三键 138 + 动作 ~70 +
中间组 ~100 + 品牌 ~140），600 时仍有余量。**不要**改用页面宫格⇄侧栏那条 900：
那条是页面布局的分界，顶栏跟着它会在 600–900 这段凭空多出一档 ✗。
（本轮顺手删掉了曾短暂存在过的 `Breakpoints.sidebarLayout = 900`。）

### 43.5.3 mac 的顺序规则

mac 风格且三键在左侧 → 顺序倒成「关闭 / 最小化 / 最大化」（mac 惯例）；
**交换位置只改顺序、不改风格** —— 这条正是 ① 号 bug 的根因所在。
