# §35 上课提醒（课前常驻通知）

> 2026-09-22 立。用户原话：「我希望在任何一节课上课前x分钟(x可设置，默认30）到上课前，移动端显示一个常驻通知，下节课的名称和教室」。
> 领域口径在 `lib/features/ims/schedule/domain/class_start_reminder.dart`（文件头有同一份口径，改动前先读）。

## 35.1 一句话口径

**每条日程排一条通知，触发时刻 = 上课时刻 − X 分钟；通知常驻到上课那一刻，由系统自动撤下。**
X 在设置页「上课提醒」节里改（默认 **30 分钟**，可选 5/10/15/20/30/45/60），关掉开关即清空全部排期。

## 35.2 为什么是「系统自动撤下」而不是排两条

窗口是 `[上课 − X, 上课)`。若按老套路「排一条开始 + 排一条撤销」，撤销那条会**多占一个系统闹钟**，
且 App 被杀 / 用户改 X 之后容易留下**撤不掉的常驻通知**（常驻通知划不掉，只能进系统设置强停 App）。

因此改用 `AndroidNotificationDetails.timeoutAfter`（`Notification.Builder.setTimeoutAfter`）：
**到点由系统撤下**，App 不必常驻、也不必记账。排期参数在
`lib/shared/services/android_notification_service.dart` 的 `_ongoingDetails({when, autoDismissAfter, countdown})`：

| 参数 | 值 | 作用 |
|---|---|---|
| `ongoing` | `true` | 划不掉的常驻（`autoCancel: false`） |
| `timeoutAfter` | `autoDismissAfter.inMilliseconds` | 上课那一刻自动消失 |
| `usesChronometer` / `chronometerCountDown` | `countdown` | 通知栏由系统走秒显示「还有多久」 |
| `onlyAlertOnce` | `true` | 只响一次（不因更新反复打扰） |
| `importance` / `priority` | `high` | 课前提醒该响一声（与「安静走秒」的实况窗区分：通道 `class_start` vs `live_class`） |

`NotificationService.scheduleAt` 新增四个**可选**参数（默认全关，既有调用方行为不变）：
`ongoing` / `autoDismissAfter` / `countdown` / `preferExact`。Windows 实现刻意忽略前三个
（toast 无常驻能力），排出来就是一条普通提醒；**课前提醒的排期本身也只跑在 Android 上**。

## 35.3 精确闹钟：能精确才精确；精确也要挑「最抗杀」的那一档

`preferExact: true` 时按 **从最可靠到兜底** 逐档尝试（`_scheduleModes` 返回一串档位，
`scheduleAt` 用 `for` 逐档 `try/catch` 降级 —— **绝不因为一档失败就整条不排**）：

| 档 | 插件枚举 | 原生调用 | 说明 |
|---|---|---|---|
| ① 系统闹钟（首选） | `AndroidScheduleMode.alarmClock` | `AlarmManager.setAlarmClock()` | 2026-10-08 加。**状态栏会出现一个闹钟图标**，系统把它当「用户看得见的闹钟」对待 —— 各 ROM 最不敢丢的一类 |
| ② 普通精确 | `AndroidScheduleMode.exactAllowWhileIdle` | `setExactAndAllowWhileIdle()` | 前一档拿不到精确闹钟授权时用（`setAlarmClock` 同样要授权） |
| ③ 非精确 | `AndroidScheduleMode.inexactAllowWhileIdle` | `setAndAllowWhileIdle()` | 最后一档：授权被拒（Android 14 起默认拒绝）时的兜底 |

`canScheduleExactNotifications()` 为 true 才给 ①②，否则只有 ③。
**不能写死精确**：Android 12+ 需要在系统设置里授权，Android 14 起默认拒绝（应用商店也限制
`USE_EXACT_ALARM` 的申请资格）。截止提醒（`deadline_reminders`）仍然只用非精确 —— 差几分钟无所谓。

> ⚠ **为什么从 `exactAllowWhileIdle` 升级到 `setAlarmClock`**：华为 / 荣耀 / HarmonyOS 上
> 「应用被从最近任务划掉后，课前提醒完全不弹」——华为官方支持文档（第三方闹钟类应用一节）
> 写明「应用不被允许后台运行、或被从后台清理时，它不会排定闹钟」。这是**系统级限制**，
> 代码绕不过去，但换一种闹钟注册方式是代码侧唯一能做的事。**根治仍要用户在系统里开
> 自启动 / 后台活动**，见 §35.12。

## 35.4 提醒列表（纯函数）

`classStartRemindersFor({entries, table, teachingWeek, now, lead, reschedules, days, max, minLead})`：

1. 逐天（默认未来 **7 天**）调 `sessionsOfDay`（**与实况窗、首页今日课程同源**：调课 / 停课 / 补课一次生效）；
2. 跳过**停课**与**已开始**的日程；
3. `when = startAt − lead`；若 `when` 已经不早于「现在 + 20 秒」（用户刚打开 App，已经进了窗口）
   → **夹到此刻**并把握手时长改成 `startAt − when`（夹完为空窗就整条丢掉）。**不补历史、也不会一进 App 弹一串**；
4. 按 `when → 课程名 → 上课时刻` 稳定排序，去重（同一节课重复解析只排一条），截断到 `max = 60` 条；
5. id = `classStartNotifyIdBase (940000) + 序号`（实况窗固定 8801、截止提醒 920000 起，三段互不重叠）。

通知文案：标题 `即将上课 · <课程名>`，正文 `<教室> · <校区> · <第X-Y节> <HH:mm-HH:mm>`。

### 教学周必须「周一对齐」推进（35.2 的真坑）

`teachingWeekOfDay({now, teachingWeek, day})` 用**两个日期各自的周一**相差几周来算，
**不能写 `teachingWeek + (day - today).inDays ~/ 7`**：那样「周日晚上看下周一」会算成同一周
（`1 ~/ 7 == 0`），单双周课会取错周次。守卫见 `test/class_start_reminder_test.dart` 的第三例。

## 35.5 排期同步（幂等）

`syncClassStartReminders(...)`（`lib/features/ims/schedule/data/class_reminder_sync.dart`）：

1. 算出期望排期；
2. `pendingScheduled()` 取系统现有排期，用 **payload**（`<epochMs>|<课程名>|<教室>|<常驻秒数>`）
   与 id 逐条对账 —— **完全一致就直接返回，一个系统调用都不发**；
3. 不一致 → 先 `cancelScheduled(本模块区间内的 id)`，再逐条 `scheduleAt(..., ongoing: true,
   autoDismissAfter: r.dismissAfter, countdown: true, preferExact: true)`；
4. 任何异常都吞掉并返回 0（提醒失败不该影响任何页面）。

`cancelClassStartReminders()` = 关开关 / 退出登录时清空本模块区间（**只删区间内的 id**，
实况窗 8801 与截止提醒的排期不受影响 —— 有守卫）。

## 35.9 已知边界

- **Android 之外不排**（Windows 桌面端只跑界面，真机提醒以 Android 为准）——与实况窗同一现状。
- **无 adb 设备时无法真机验收**：本机 `adb devices` 为空，本轮只做到「领域 + 同步 + 设置页」三层自动验证，
  外加在**真实数据**上跑一遍期望排期（见 §35.10）。手机上要看的四件事：① 上课前 X 分钟出现常驻通知；
  ② 内容 = 课程名 + 教室；③ 上课那一刻自动消失（不用手动划）；④ 通知栏上是倒计时走秒。
- 提前量**只影响窗口起点**，不改课程的起止时刻；实况窗（上课中倒计时）与它是两条独立通道。
- **华为 / 荣耀上「应用被从最近任务划掉后不弹」是系统限制**（官方文档口径），代码侧只能
  换闹钟注册档 + 把用户送到系统设置页 —— 根治要用户自己开自启动 / 后台活动，见 §35.12。
- 通知点击目前**不跳转页面**（插件未接 `onDidReceiveNotificationResponse`）；要做得单独排期。
- 提醒窗口是「未来 7 天滚动」，**App 连续 7 天没打开过，第 8 天的课就没有提醒**（回前台即补齐）。

## 35.11 Android 真机验证（2026-09-23 · 华为 Mate 30 Pro / LIO-AN00 / Android 12 · SDK 31）

一次完整的「装上手机 → 排期 → 出现 → 自动消失」实测（`flutter run -d <设备序列号>`，
debug 包覆盖旧 debug 签名包，**不用卸载** → 手机数据保留）：

| 环节 | 读数 | 判定 |
|---|---|---|
| App 首帧重排 | `I/flutter: 🔔 课前提醒已排期 9/9 条`（真机课表比 PC 缓存多 2 节） | ✓ |
| 系统里的排期 | `pendingScheduled()` → `total=9 mine=9 ids=940000,940001,…,940008` | ✓ id 全在本模块区间 |
| AlarmManager | `dumpsys alarm` 里 `RTC_WAKEUP … ScheduledNotificationReceiver` | ✓ 真排进了系统 |
| 常驻通知出现 | 精确闹钟（`preferExact: true`）+6 秒 → +12 秒 `dumpsys notification` 命中 `android.title=String (即将上课 · 测试课程)` | ✓ |
| **到点自动消失** | 同一 dump 在 +40 秒（`timeoutAfter: 20s`）命中 **0** | ✓ 设计成立 |

### ⚠ 本设备上踩到的唯一坑：非精确闹钟会被系统批处理推迟

- 首版 `sendTestClassReminder` **没传 `preferExact`** → 走 `inexactAllowWhileIdle` → 排的是 **5 秒后**
  的闹钟，实测 **+10 秒通知根本没出现**（`queued=true` 但系统里查不到），
  看起来就像「功能坏了」。改成 `preferExact: true` 后同一条路径 +12 秒就出现了。
- 教训：**凡「用户马上要看结果」的提醒都必须精确**（测试按钮、以及真提醒本来就已经是
  `preferExact: true`）；`inexact` 只适合「迟到几分钟无所谓」的场景（截止提醒仍用它）。
  `SCHEDULE_EXACT_ALARM` 已在 `android/app/src/main/AndroidManifest.xml` 声明，
  拿不到权限时 `_scheduleModes` 自动退回非精确。
- 顺带核实：`POST_NOTIFICATIONS` **无需自己声明** —— 它由 `flutter_local_notifications` 的
  插件清单合并进来（`aapt2 dump badging app-release.apk` 实测有 ✓）；Android 12 上该权限还不需要运行时授权。

### 手机端自查入口（用户可自助）

设置页 →「上课提醒」→ **发送测试提醒**（`Key('classReminderTest')`）：5 秒后弹出常驻通知、
15 秒后自动消失。Android 13+ 需先允许通知；国产 ROM（华为 / 小米等）还需在
「设置 → 电池 → 应用启动管理」里允许本应用自启动 / 后台活动，否则闹钟会被省电策略清掉。

## 35.12 ⚠ 华为 / 荣耀：应用被划掉后不弹（2026-10-08 处置 · 根因 + 两层补救）

**用户报告**：「应该在上课前 30 分钟弹消息，但是应用不在后台就不生效」（机型 = 华为 / 荣耀）。

### 根因（不是代码缺陷，是系统限制）

闹钟**排得进系统**（§35.11 的 `dumpsys alarm` 已证），但**华为在用户从最近任务划掉应用后，
不再把这个应用的闹钟交给它**。华为官方支持文档 *The alarm does not go off as scheduled*
（**第三方闹钟类应用**一节）原话：

> If the app is not allowed to run in the background, **or is cleared from the background,
> it will not schedule an alarm.** —— 解法是 ① 设置里允许**自启动 / 关联启动 / 后台活动**；
> ② 最近任务里**下拉锁定**；③ 允许开机启动。
> 来源：<https://consumer.huawei.com/sg/support/content/en-gb00409667/>

分类定位：闹钟注册在**系统进程**里、不随 App 进程消失，到点由系统发广播唤醒
`ScheduledNotificationReceiver`；卡住的是「**系统肯不肯唤醒一个已被划掉的应用**」这一步。
所以「App 开着 / 在后台时照常弹，划掉后彻底没反应」正是这个根因的典型表现。
横向对照：微信这类应用靠**厂商推送**兜底（通知由系统进程直接画，与应用死活无关），
本地闹钟是另一条路 —— 我们只有后者，这在纯客户端项目里是合理取舍（接华为 Push Kit 要
AGC 应用 + 签名指纹 + `agconnect-services.json` 入库 + 服务端，与公开仓库的隐私纪律 §34 冲突）。

### 代码侧补救（两层）

**① 换一种闹钟注册方式**（`AndroidNotificationService._scheduleModes`，见 §35.3）：
精确档首选 `AndroidScheduleMode.alarmClock`（`AlarmManager.setAlarmClock()`）。
`setAlarmClock` 是「**用户可见的闹钟**」—— 状态栏会出现闹钟图标，系统当它是起床闹钟那一类，
各 ROM 最不敢丢。**代价 = 那个图标**（每条提醒到点后消失，下一条又出现）。
拿不到精确闹钟授权时自动落到 `exactAllowWhileIdle`，再不行落 `inexactAllowWhileIdle`。

**② 把用户送到系统设置页**（`SettingsClassReminderProtectHint` + `AppSettingsGuide`）：
设置页「上课提醒」卡底部多一段说明与两个按钮（`Key('classReminderOpenStartup')` /
`Key('classReminderOpenBattery')`），文案随 `Build.MANUFACTURER` 换一版
（华为 / 荣耀点名「应用启动管理」并写清「最近任务下拉锁定」；其它品牌走通用说法）。

- Dart 侧 = `lib/core/platform/app_settings.dart`（`AppSettingsGuide.isSupported` /
  `openBackgroundSettings()` / `openBatterySettings()` / `manufacturer()`），
  通道 `smarter_jxufe/app_settings`，任何异常都收敛成「未打开」不外抛。
- 原生 = `android/app/src/main/kotlin/.../settings/AppSettingsBridge.kt`，候选**按顺序**
  逐个 `resolveActivity` 再 `startActivity`（**不判断 ROM 品牌**）：
  ① 华为 / 荣耀 `com.huawei.systemmanager.startupmgr.ui.StartupNormalAppListActivity`
  （+ `…ActivityEx`）→ ② 小米 `com.miui.permcenter.autostart.AutoStartManagementActivity`
  → ③ 品牌私有 action（`com.huawei.systemmanager.startupmgr.action.ALLOW_STARTUP` /
  `SHOW_STARTUP_APPS`）→ ④ **`ACTION_APPLICATION_DETAILS_SETTINGS`（任何 Android 都有）**
  → ⑤ 电池优化列表。
- 电池优化刻意只用 `ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS`（**官方设置列表页**）：
  「直接申请忽略优化」那条要 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 权限，Google Play 有政策限制，
  本项目不引这个隐患（见桥里注释）。
- 卡片自己**不判平台**（老守卫钉着）：门控是 `AppSettingsGuide.isSupported`，
  桥内部才是 `!kIsWeb && Platform.isAndroid`；桌面端整块引导不渲染。

### 用户侧仍需自己做（没有任何 API 能代劳）

华为 / 荣耀：**设置 → 应用 → 应用启动管理** → 关掉「自动管理」→ 打开**自启动 / 关联启动 /
后台活动**；再在**最近任务里把本应用下拉**（出现锁图标即锁定）。小米：自启动 + 省电策略
「无限制」。做完这些，划掉应用后闹钟才会照常触发。
