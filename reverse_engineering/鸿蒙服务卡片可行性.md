> 对象：`D:\Project\Ongoing\smarter_jxufe`（Flutter 客户端「智慧er江财」，包名 `com.example.smarter_jxufe`，现有 Android + Windows 两个平台产物）

> 调研日期：2026-09-19　调研方式：华为开发者文档正文 API + OpenHarmony 官方文档仓 markdown + adb 真机实测

## 1. 结论摘要

| # | 问题 | 结论 | 一句话依据 |
|---|---|---|---|
| 1 | 安卓 APK（含 Flutter 打的包）能否在 HarmonyOS 4.x 提供「服务卡片」 | **不能。** 服务卡片**只能**由鸿蒙应用（HAP）或元服务提供 | 卡片提供方必须实现 `FormExtensionAbility` 生命周期 + `form_config.json`，这两者都是 HAP 工程机制；APK 只能注册 `AppWidgetProvider`，在鸿蒙桌面落到「窗口小工具」另一栏 |
| 2 | 鸿蒙 4.x 与 NEXT(5+) 的卡片能力差别 | **同一套 Form Kit，但 SDK 能力面差 3 代以上**（互动卡片/独立卡片包/多定点刷新等大量特性是 API 12/15/18/20/22/23 才有的） | 华为官方版本表里 HarmonyOS 4.x 只对应 **API 9**（DevEco Studio 3.1 Release），而 NEXT 线是 5.0.0=API 12 起 |
| 3 | 高 API level 编出的 HAP 能否装到 HarmonyOS 4.2 | **不能。** 装不进去 | `compatibleSdkVersion` 打包成 `minAPIVersion`，「设备系统搭载的 API 版本不能低于该字段的值，低于则无法安装」；真机实测该机器 HAP 运行时 API 版本只有 **8/9** |
| 4 | Flutter 应用上鸿蒙现状 | 生态可用但**版本对不上本项目**：官方分支有 3.35.7 / 3.41.9 / 3.44.9-dev，**没有 3.38.x**，而本项目是 Flutter 3.38.7 | `flutter_flutter` 分支与 README；`flutter build hap` 输出 HAP 走 DevEco 5.0/API12 工具链 |
| 5 | 插件缺失 | 本项目 **47 个直接依赖**里：**14 个官方已 ohos 适配**（改 `git:` 引用即可）、**~26 个纯 Dart 天然可用**、**4 个推断可用待实测**、**1 个（`pdfrx`）明确无适配** | OpenHarmony-Flutter 官方适配清单逐条比对（见 §4.2） |

**推荐路线（详见 §6）：维持现状 + 安卓侧增强（路线 d）为唯一低成本可落地项；「只做鸿蒙壳应用专供服务卡片」（路线 b）在本机（HarmonyOS 4.2 / API 8-9）上属于高成本且工具链已停止演进的死路，不建议投入。**

**量级预估**

| 路线 | 工作量 | 可行性（针对本机 HarmonyOS 4.2） |
|---|---|---|
| a. 全量鸿蒙移植 | 6–12 人月（Flutter 3.38.7→3.35.7/3.41.9 降/升级 + 47 依赖盘点 + 重写 1 个原生插件 + 全部测试回归） | **不可行**：产物最低 API 12，装不进 API 8/9 的设备 |
| b. 只做鸿蒙「壳」应用专供卡片 | 3–6 人周（ArkTS 卡片 + 登录/接口重写），但需先解决 API 9 工具链 | **高风险**：需 DevEco Studio 3.1（2023 年，已停止演进），且本机 API 版本实测为 8/9，能否装上需实测 |
| c. 快应用 / 元服务卡片 | 2–4 人周（快应用卡片）；元服务卡片同 b | 快应用侧「卡片」是嵌入超级 APP 的形态，**与桌面服务卡片不是一回事**（见 §2.5） |
| d. 维持安卓小部件 + 增强 | 1–3 人天/项 | **完全可行**，见 §5.4 |

### 2.1 问题 1：安卓 APK 能否提供「服务卡片」？→ **不能**

**依据 A：卡片提供方的定义就排除了 APK。**（华为官方文档 [Form Kit术语](https://developer.huawei.com/consumer/cn/doc/HarmonyOS-Guides/form-glossary)）

> **Widget Provider；卡片提供方**
> 提供卡片显示内容的**应用或元服务**，是卡片功能的具体实现者。负责设计实现卡片 UI、数据更新以及点击交互处理功能，**实现 FormExtensionAbility 生命周期接口**来管理卡片的创建、更新、删除等操作。

（华为官方文档 [Form Kit简介](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/formkit-overview)）

> 支持开发卡片应用类型：**应用和元服务内均支持开发卡片。**
> 支持卡片使用位置：用户可以在桌面、锁屏等系统应用上添加使用，**不支持在普通应用内嵌入显示卡片**。

`FormExtensionAbility` 属于 Ability Kit 的 Extension 能力，只能在 HAP 工程的 `module.json5` 的 `extensionAbilities`（Stage 模型）或 `config.json` 的 `abilities`（FA 模型）中声明 —— 这是 HAP 专有清单结构，**APK 没有对应物**。

**依据 B：卡片配置是 HAP 工程内的一份 profile 文件。**（华为官方文档 [配置ArkTS卡片的配置文件](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/arkts-ui-widget-configuration)）

```json5
{
  "module": {
    "extensionAbilities": [{
      "name": "EntryFormAbility",
      "srcEntry": "./ets/entryformability/EntryFormAbility.ets",
      "type": "form",
      "metadata": [{ "name": "ohos.extension.form", "resource": "$profile:form_config" }]
    }]
  }
}
```
`form_config.json` 位于 HAP 工程的 `resources/base/profile/` 下。APK 的 `AndroidManifest.xml` 无法声明 `type: "form"` 的 ExtensionAbility，自然也无法提供 `$profile:form_config`。

**依据 C：真机上两套框架是物理分开的（本文实测，用户已复核）。**

| 实测项 | 结果 |
|---|---|
| 设备 | `LIO-AN00`，`hw_sc.build.platform.version = 4.2.0`，`ro.build.version.release = 12`，`ro.build.version.sdk = 31` |
| HAP 应用清单 | `adb shell /system/bin/bm dump -l` → **32 个鸿蒙应用**（`com.huawei.ohos.mms`、`com.huawei.ohos.camera`、`com.huawei.ohos.photos`、`com.huawei.calendar`、`com.huawei.android.totemweather`、`com.huawei.ohos.suggestion`…）；`bm dump -t com.huawei.ohos.mms` → `true`（是鸿蒙应用）；`bm dump -p` → `/system/priv-app/HwMmsHm/entry-release-rich.hap` |
| 服务卡片声明位置 | 全部在上述 **HAP 的 `config.json`/`pack.info` 的 `abilities[].forms[]`** 里（例：日历 11 张卡片 `AgendaCard_2X2`/`MonthView_4X4`/`courseTable`…；天气 11 张；备忘录 5 张）；`com.huawei.android.totemweather` 的 HAP 与 APK 同名但卡片挂在 HAP 上 |
| 启动器字符串 | `com.huawei.android.launcher`（`/system/app/HwLauncher6/base-master.apk`）：**「服务卡片 / Service widgets」** 与 **「窗口小工具 / Widgets」** 是两套独立文案；引导语「To add this widget again, pinch with two fingers on the home screen, then go to **Service widgets > Widgets**」 |
| 卡片尺寸文案 | 微卡片 = `Mini service widget`、小卡片 = `Small service widget`、中卡片 = `Medium service widget`、大卡片 = `Large service widget`；另有「上滑应用图标呼出服务卡片」「更多服务卡片」「堆叠卡片」「组合卡片」 |
| 卡片框架（安卓侧桥接） | `com.huawei.hicard`（`/system/priv-app/HiCard/HiCard.apk`，`minSdk=25 targetSdk=28`，导出 `holder.HiCardService` + `provider.HiCardProvider`，权限 `com.huawei.hicard.permission.READ_HICARD_PROVIDER`） |

**结论**：在鸿蒙桌面上，**APK（含 Flutter 打的包）只会出现在「窗口小工具」栏**，即我们现在的形态；「服务卡片」是与 HAP 的 `FormExtensionAbility` 绑定的另一套框架。**没有任何配置或权限能让 APK 提供「服务卡片」。**

### 2.2 问题 2：鸿蒙 4.x 与 NEXT(5+) 的卡片能力差别 / API level 对应 / 高 API HAP 能否装低版本设备

**依据 A：华为官方版本表**（[所有HarmonyOS开发套件版本](https://developer.huawei.com/consumer/cn/doc/doccenter-release-notes/overview-allversion)，`updatedDate=2026-08-29`，原文节选）

| HarmonyOS 开发者版本（即 API 版本） | DevEco Studio 版本 | 发布时间 |
|---|---|---|
| 26.0.0 | DevEco Studio 26.0.0 Release | 2026/08/28 |
| 6.1.1(24) | DevEco Studio 6.1.1 Release | 2026/05/26 |
| 6.1.0(23) | DevEco Studio 6.1.0 Release | 2026/04/20 |
| 6.0.2(22) | DevEco Studio 6.0.2 Release | 2026/01/21 |
| 6.0.1(21) | DevEco Studio 6.0.1 Release | 2025/11/20 |
| 6.0.0(20) | DevEco Studio 6.0.0 Release | 2025/09/25 |
| 5.1.1(19) / 5.1.0(18) / 5.0.5(17) / 5.0.4(16) / 5.0.3(15) / 5.0.2(14) / 5.0.1(13) / **5.0.0(12)** | 对应 DevEco Studio 各版本 | 2025/06/30 → 2024/10/22 |
| **HarmonyOS 3.1/4.0（API 9）** | **DevEco Studio 3.1 Release** | **2023/05/15**（版本使用建议：NA） |

**关键点：这张官方表里没有 HarmonyOS 4.2 这一行。** 4.2 属于 4.x 遗留线，其开发套件就是 **API 9（DevEco Studio 3.1）**，且已被标记为 NA（不再推荐）。NEXT 线（5.0.0=API 12 起）是**另一条设备线**。

**依据 B：真机实测该设备的 HAP 运行时 API 版本 = 8/9**（华为文档中查不到，本文实测）

```
adb shell getprop | grep -E 'apiversion|os.version|releasetype'
  [hw_sc.build.os.apiversion]: [8]
  [hw_sc.build.os.version]: [3.0.0]
  [hw_sc.build.os.apireleasetype]: [Release]
  [hw_sc.build.platform.version]: [4.2.0]
  [persist.sys.ohc.apiversion]: [9]
  [persist.sys.ohc.releasetype]: [Release]
```
两个属性给出 8 与 9，**均远低于 12**。（官方定论命令是 `hdc shell param get const.ohos.apiversion`，本机 `adb shell` 里没有 `param` 二进制，需装 DevEco/hdc 后复核。）

**依据 C：安装兼容性由 `compatibleSdkVersion` 决定**（华为官方 FAQ [低版本手机应用市场是否能搜索到高版本应用](https://developer.huawei.com/consumer/cn/doc/doccenter-dev-faq/faqs-appgallery-24)）

> `compatibleSdkVersion`：打包后在 module.json 文件中的字段为 `minAPIVersion`，应用运行要求的最低 SDK 版本。**该字段决定了打包的应用的 API 版本。运行该应用的终端设备系统搭载的 API 版本不能低于该字段的值，低于则无法安装。**
> 例如：`compatibleSdkVersion` 设置为 11，在 API 12 的手机能搜索到应用，也能正常安装；但设置为 13 时，在 API 12 的手机能搜索到应用，但当用户点击安装此应用时，会提示此应用「无法安装」并给出所需要的系统版本要求。
> 三个 SDK 版本属性之间的大小关系为：`compatibleSdkVersion ≤ targetSdkVersion ≤ compileSdkVersion`

（华为官方 FAQ [安装HAP时提示「compatibleSdkVersion and releaseType of the app do not match the apiVersion and releaseType on the device.」](https://developer.huawei.com/consumer/cn/doc/harmonyos-faqs-V14/faqs-app-debugging-22-0000001940675226-V14)）

> 出现该问题是因为**当前工程配置的最低兼容版本高于设备镜像版本**。使用命令 `hdc shell param get const.ohos.apiversion` 查询当前设备的 API 版本，并对比工程级 `build-profile.json5` 配置文件中的 `compatibleSdkVersion` 字段。如果版本不匹配：方法一：升级设备镜像版本；**方法二：降低工程的 API 版本**（Compatible SDK 选择更低的版本号，以兼容设备的 API 版本）。

**依据 D：华为自己已经不再统计 4.x 设备**（[存量设备API版本使用数量参考](https://developer.huawei.com/consumer/cn/doc/doccenter-release-notes/sdk-version-percentage)，截止 2026-09-06）

> 表格只有 7.0.0(26.0.0)=5.27%、6.1.1(24)=86.82%、6.1.0(23)=5.50%、6.0.2(22)=1.58%、6.0.1(21)=0.41%、6.0.0(20)=0.04%、5.1.1(19)=0.10%、5.1.0(18)=0.07%、5.0.5(17)=0.21%，其余 5.0.x 全为 0%。
> **HarmonyOS 4.x / API 9 及以下完全不在表内。**

**依据 E：同一套 Form Kit，但能力面差好几代。** 以下字段/能力均标注了起始 API，API 9 设备全部不可用：

| 卡片能力 | 起始 API |
|---|---|
| `dataProxyEnabled`（卡片代理刷新） | API 12 |
| `renderingMode`（autoColor/fullColor/singleColor，可上锁屏） | API 15 |
| `multiScheduledUpdateTime`（多定点刷新，最多 24 个时刻） | API 18 |
| `conditionUpdate: ["network"]`（网络条件刷新） | API 18 配置、**API 26.0.0 起才生效** |
| 独立卡片包（`formWidgetModule`/`formExtensionModule`） | API 20 |
| `resizable` / `groupId`（拖拽改尺寸、卡片组） | API 20 |
| **互动卡片（破框动效）** | API 20 |
| `formProvider.reloadForms` / `reloadAllForms`（批量刷新） | API 22 |
| `supportDeviceTypes` / `supportDevicePerformanceClasses` | API 22 |
| `standby`（待机屏保卡片） | API 23 |
| `enableBlurBackground`（模糊背板，仅旗舰） | API 23 |
| `colorMode` | API 12 支持、**API 20 废弃** |

**结论**：
- Form Kit 是**同一个 Kit 名称、同一条 API 演进线**，但 API 9（鸿蒙 4.x）与 API 12+（NEXT）之间是**能力差好几代的两套 SDK 面貌**。
- 用 DevEco Studio 5.x/6.x（API 12 起）编出的 HAP **无法安装到 HarmonyOS 4.2 设备**（FAQ 原文 + `minAPIVersion` 规则）。要装到 4.2，必须把 `compatibleSdkVersion` 降到 ≤9，而官方登记的 API 9 工具链是 **DevEco Studio 3.1 Release（2023/05/15）**。

### 2.3 问题 3：Form Kit 卡片开发要点

#### 2.3.1 `form_config.json` 关键字段（华为官方文档 [配置ArkTS卡片的配置文件](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/arkts-ui-widget-configuration)）

**卡片五元组**（原文）：「五元组分别为 bundleName、moduleName、abilityName、formName、formDimension …… **五元组不建议使用资源文件导入配置** …… **如果应用升级后五元组有改变，系统中对应的卡片会被删除，在屏幕上会消失。**」

| 字段 | 含义 / 取值 | 备注 |
|---|---|---|
| `forms` | 全部卡片配置数组 | **最多支持配置 16 个卡片，若超过 16 个，则保留配置的前 16 个** |
| `name` / `displayName` / `description` | 卡片名 / 卡片管理页展示名（≤30 字节）/ 描述（≤255 字节） | 建议用 `$string:` 资源索引做多语言 |
| `src` | 卡片 UI 代码完整路径 | ArkTS 卡片须带后缀：`"./ets/widget/pages/WidgetCard.ets"` |
| `uiSyntax` | `arkts` 或 `hml` | 缺省 `hml` |
| `window` | 设计基准宽/自动宽 | **仅对 JS 卡片生效** |
| `isDefault` | 是否默认卡片 | **每个应用有且只有一个默认卡片**；「应用上架时每个应用只允许配置一张默认卡片」 |
| `supportDimensions` | `1*2`(1行2列二宫格) / `2*2`(四宫格) / `2*4`(八宫格) / `2*3`(六宫格) / `3*3`(九宫格) / `4*4`(十六宫格) / `6*4`(二十四宫格) | 「**2\*3 和 3\*3 仅支持手表设备**」 |
| `defaultDimension` | 默认尺寸 | 必须在该卡片 `supportDimensions` 列表内 |
| `updateEnabled` | 是否支持周期性刷新（定时+定点） | `true` 时 `updateDuration` / `scheduledUpdateTime` 任选其一 |
| `scheduledUpdateTime` | 定点刷新时刻，24 小时制精确到分钟，如 `"10:30"` | 缺省 `"0:0"` 不刷新 |
| `updateDuration` | **定时刷新周期，单位 30 分钟**；正整数 N = 30×N 分钟；0 不生效 | **优先级高于 `scheduledUpdateTime`**（要定点必须把它配成 0） |
| `formConfigAbility` | 桌面点「编辑」拉起的 ability，URI 格式 | 可缺省 |
| `dataProxyEnabled` | 卡片代理刷新（API 12 起） | 置 true 时「定时刷新和下次刷新不生效，但不影响定点刷新」 |
| `isDynamic` | `true` 动态卡片 / `false` 静态卡片 | 仅对 ArkTS 卡片生效，缺省 true |
| `fontScaleFollowSystem` / `supportShapes` / `previewImages` | 字体跟随系统 / 形状 `rect`\|`circle` / 预览图 | 缺省 `true` / `["rect"]` / `[]` |
| `renderingMode`（API15）、`multiScheduledUpdateTime`（API18）、`conditionUpdate`（API18/26.0.0）、`resizable`+`groupId`（API20）、`supportDeviceTypes`（API22）、`standby`（API23）、`enableBlurBackground`（API23） | 见 §2.2 依据 E | 新特性，API 9 无 |

`module.json5` 侧的对应配置（原文示例）：
```json5
"extensionAbilities": [{
  "name": "EntryFormAbility",
  "srcEntry": "./ets/entryformability/EntryFormAbility.ets",
  "label": "$string:EntryFormAbility_label",
  "type": "form",
  "metadata": [{ "name": "ohos.extension.form", "resource": "$profile:form_config" }]
}]
```

#### 2.3.2 FormExtensionAbility 生命周期（华为官方文档 [管理ArkTS卡片生命周期](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/arkts-ui-widget-lifecycle)）

| 回调 | 触发时机 | 关键说明 |
|---|---|---|
| `onAddForm(want: Want): formBindingData.FormBindingData` | 卡片使用方创建卡片时 | **必须返回** `formBindingData.createFormBindingData(obj)`；入参 `want.parameters[formInfo.FormParam.NAME_KEY]` 可拿卡片名 |
| `onCastToNormalForm(formId: string): void` | 临时卡片转常态卡片 | **官方原文：「当前卡片使用方不会涉及该场景，无需实现该回调函数」** |
| `onUpdateForm(formId: string): void` | 定时/定点/使用方请求更新时 | 在回调内调 `formProvider.updateForm(formId, formData)` |
| `onFormEvent(formId: string, message: string): void` | 卡片内 `postCardAction` 的 `message` 事件 | 卡片上有按钮 → message → 这里收 → `updateForm` 推数据 |
| `onChangeFormVisibility(newStatus: Record<string, number>): void` | 卡片可见性变化 | **仅系统应用生效** |
| `onRemoveForm(formId: string)` / `onConfigurationUpdate(config)` / `onAcquireFormState(want): formInfo.FormState` | 删除 / 配置变化 / 查询状态 | `onAcquireFormState` 默认返回 `FormState.READY` |

> **进程模型（原文，最关键的一条约束）**：「FormExtensionAbility **进程不能常驻后台**，即在卡片生命周期回调函数中无法处理长时间的任务，在生命周期调度完成后会继续存在 **10 秒**，若在 10 秒内未收到新的生命周期回调，则进程将自动退出。针对可能需要 10 秒以上才能完成的业务逻辑，建议**拉起主应用**进行处理，处理完成后使用 `updateForm` 通知卡片进行刷新。」
> `onConfigurationUpdate` 注释亦写：「formExtensionAbility 创建后 **10 秒内无操作将会被清理**」。

**实践含义**：卡片刷新时拉一次 HTTP（秒级）没问题；CAS 登录跳转、MFA、长轮询这类必须在主应用里做完再把结果推进卡片。

#### 2.3.3 ArkTS 卡片 UI 的能力边界（华为官方文档 [ArkTS卡片概述](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/arkts-form-overview)）

**约束与限制（原文逐条）**：
> - 当前**仅支持基于 ArkUI 框架开发卡片，暂不支持跨平台开发**。
> - 当导入模块时，**仅支持导入标识「支持在ArkTS卡片中使用」的模块**。若使用了不支持使用的 API，**卡片加载显示异常**。
> - 支持导入 **HAR** 静态共享包，**不支持导入 HSP** 动态共享包。
> - **不支持使用 native 语言开发，不支持加载 native so。**
> - 卡片组件内容的事件处理和卡片使用方的事件处理是独立的，为防止手势冲突，**卡片内不支持左右滑动的控件**。
> - 不支持极速预览 / 不支持断点调试能力 / 不支持 Hot Reload 热重载 / **不支持 `setTimeout`**。

**渲染机制**：ArkTS 卡片的 UI 代码（`widget.abc`）运行在**系统公共的 FRS 进程**内；同一提供方的渲染实例跑在同一个 ArkTS 虚拟机，`globalThis` 同提供方共享、不同提供方隔离。
**数据交互**（[ArkTS卡片页面刷新概述](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/arkts-ui-widget-interaction-overview)原文）：「由于卡片提供方和卡片为相互独立的进程，两者间的数据共享**只能通过 `LocalStorageProp` 传递，不能使用 `getContext` 方法**。……接收数据时，卡片数据会被转换成 string 类型。」

| 能力 | 能不能用 | 依据 |
|---|---|---|
| **列表** | ✅ 可用 | `List` 文档带「卡片能力」标记（`从API version 9/14/18/19/20/22开始，该接口支持在ArkTS卡片中使用`） |
| **滚动容器 `Scroll`** | ❌ 不可用 | `Scroll` 组件文档**没有任何「卡片能力」标记**（与「卡片内不支持左右滑动的控件」一致） |
| **网格 `Grid`** | ❌ 不可用 | `Grid` 文档同样**无卡片能力标记** |
| **自定义绘制（画图表）** | ✅ 可用 | `Canvas` 从 **API 9** 起支持在 ArkTS 卡片中使用（属性动画/显式动画同理） |
| **图片 / 文本** | ✅ 可用 | `Image` / `Text` 均有 API 9 起的卡片能力标记 |
| **Swiper（轮播）** | ⚠️ 部分可用 | 有多个「卡片能力」标记（API 7/10/12/15/18/19/20/22/23/24），需逐接口核对 |
| **卡内直接发网络请求** | ❌ **不可以** | 见下 |
| **卡内交互回传** | ✅ 可用（3 种事件） | `postCardAction(this, {action:'router'\|'message'\|'call', params:{...}})`，**仅在卡片控件的点击事件中可以调用**；静态卡片用 `FormLink` 组件 |

**关于「卡内能否发网络请求」的直接证据（本文实测）**：
- 华为官方 [`@ohos.net.http` (数据请求)](https://developer.huawei.com/consumer/cn/doc/harmonyos-references/js-apis-http) 文档正文（286,605 字节 HTML / 79,768 字符纯文本）中 **「卡片」出现次数 = 0** —— 该模块**没有**「支持在 ArkTS 卡片中使用」标记。
- 结合前述硬规则「仅支持导入标识『支持在ArkTS卡片中使用』的模块 …… 否则**卡片加载显示异常**」，可判定：**卡片 UI 内不能直接做 HTTP 请求**，正确做法是在 `FormExtensionAbility`（或主应用）里请求，再用 `formProvider.updateForm` 把结果推给卡片（`LocalStorageProp` 接收）。
- 交叉印证（二手，仅作旁证）：华为云社区文章《开发者技术支持-鸿蒙服务卡片请求网络数据与网络图片解决方案》、《卡片中如何获取上下文对象呢》问答，均指向「卡片拿不到 context / 不能直接请求网络」。

### 2.6 补充证据：华为官方博客《Flutter + 鸿蒙 | 服务卡片开发干货（一）》（用户 2026-09-19 提供）

来源 <https://developer.huawei.com/consumer/cn/blog/topic/03187302625490272> ——《Flutter + 鸿蒙 | 服务卡片开发干货（一）》，作者 **董乐乐**（Lv7），发布于 **2025-07-07 20:30 广东**。系列：上一篇《Flutter + 鸿蒙 | Flutter 跳转鸿蒙原生界面》；本篇承诺的「第二篇」= ① 响应服务卡片指令（快捷跳转到指定 Flutter 界面）② **Flutter 应用内把服务卡片添加到桌面**。
（取证：华为 blog 是纯前端渲染 —— 直抓只有 1,952 B 壳，`documentPortal/getDocumentById` 对 blog 无效（`{"code":92531031,"message":"document not found"}`），blog 自己的接口在 `main.744fb9e0fadb358c.js` 里（`partnerblogservice/v1/openblog/getBlogInfoById` 等，经 `{serverUrl}/community/servlet/consumer/…`）；最终用 **headless Chrome + CDP**（`--headless=new --remote-debugging-port --remote-allow-origins=*`，显式 `Page.navigate` + UA 覆盖）渲染后取 `document.body.innerText`，正文 7,732 字符，已存 `%TEMP%\_hwblog_article.txt`，脚本 `%TEMP%\_hwblog_cdp2.py`。）

**这篇讲什么**：把 Flutter 里的数据经原生侧传给 FormKit 服务卡片的完整链路 —— 正是本文路线 b 最缺的那一环。给出的四段式：

1. **卡片工程侧**：对 `entry/src/ets` 右键 → *Service Widget* → **Dynamic Widget**；新增 `resource/base/profile/form_config.json`：
   ```json
   {"forms":[{"name":"anniversary","displayName":"$string:anniversary_display_name",
     "description":"$string:anniversary_desc","src":"./ets/anniversary/pages/AnniversaryCard.ets",
     "uiSyntax":"arkts","window":{"designWidth":720,"autoDesignWidth":true}}]}
   ```
   （`uiSyntax:"arkts"` = ArkTS 卡片；`src` 指向卡片 UI 的 `.ets`。）
2. **Flutter 端**：工具类 `HomeWidgetUtils.pinCard(context, name, date, image)` → `MethodChannel("plugins.flutter.io/home_widget").invokeMethod("setPin", {"card": {"name":…,"date":…,"image":…}})`（channel 名必须与原生侧常量一致；注意这正是 **`home_widget` 插件的既有 channel 路径**）。
3. **鸿蒙原生端**：`class HomeWidgetPlugin implements FlutterPlugin, AbilityAware` 在 `onAttachedToEngine` 里 `new MethodChannel(binding.getBinaryMessenger(), "plugins.flutter.io/home_widget")`，挂 `HomeWidgetHandlerImpl implements MethodCallHandler`；`onMethodCall` 里 `switch (call.method) { case "setPin": … }` 把 `call.argument('card')` **写进鸿蒙侧 SharedPreferences**（`preferenceUtils.putPreferenceValue('pin', 'name', …)`）。
4. **卡片数据源**：`ets/EntryFormAbility.ets` 的 `onUpdateForm / onFormEvent / onAddForm` 读 SharedPreferences → `let data = await this.getPinData(formId)` → `formData = formBindingData.createFormBindingData(data)` → `formProvider.updateForm(formId, formData)`。

**对我们的直接意义（三条，含一条成本修正）**

- ✅ **数据桥可以照搬**：我们 Android 侧已有同构实现（`lib/features/home_widget/data/home_widget_bridge.dart` 的 `MethodChannel('smarter_jxufe/home_widget')` + Kotlin `HomeWidgetStore` / `MetricWidgetRenderer` 的 RemoteViews），移植到鸿蒙只需把「Kotlin + RemoteViews + SharedPreferences」换成「ArkTS + ArkUI 卡片 + preferences + `formProvider.updateForm`」。
- ✅ **数据准备不必在 ArkTS 重写**（§5.2 原先估的主要工作量）：这篇文章的做法是「**Flutter 算好、原生只存/只渲染**」，而本项目已有 `lib/features/home_widget/data/home_widget_sync.dart` 的 `HomeWidgetSnapshot`（电费 / 网费 / 课程加权 / 志愿时长 / 今日课程，含 10 分钟节流与未登录不推）—— 于是 **CAS+MFA 会话、GBK 解码、4 个接口都不必在鸿蒙侧重造**。⚠ 前提是 **Flutter 应用本身跑在鸿蒙上**（= 路线 a 的产物，API 12+）；若走「独立 HAP 壳」，它拿不到 Android 应用的沙箱数据，仍需自建会话/接口，或改用公共目录 JSON 传递（见下）。
- ⚠️ **不推翻两条硬结论**：文章前提是**已经存在鸿蒙工程**（`entry/src/ets`、`EntryFormAbility.ets`、HAP 内的 `form_config.json`），**APK 依旧给不出服务卡片**；它发布于 2025-07（DevEco 5.x / API 12+ 时代），「API 8/9 设备装不进高 API 产物」那道墙不变。
- 🔎 **新增待验证点（并入阶段 0）**：独立 HAP 壳能否通过**公共目录 JSON** 取数据（Android 应用写 `/storage/emulated/0/…` 公共目录、HAP 侧读）—— 若可行，路线 b 的 ArkTS 侧只剩「读 KV + 画卡片」，工作量从 3–6 人周降到 **~1–2 人周**（不含工具链攻关）。

## 3. Form Kit 卡片能力与限制（速查卡）

```
卡片提供方（HAP / 元服务）
  ├─ module.json5: extensionAbilities[{ type:"form", srcEntry:"...EntryFormAbility.ets", metadata:[{name:"ohos.extension.form", resource:"$profile:form_config"}] }]
  ├─ resources/base/profile/form_config.json   ← 最多 16 张卡片 / 只 1 张 isDefault
  ├─ EntryFormAbility.ets  (extends FormExtensionAbility)  ← 回调后最多活 10 秒
  └─ WidgetCard.ets        (@Entry 卡片 UI，运行在系统 FRS 进程)

数据流：FormExtensionAbility --formProvider.updateForm--> 卡片 LocalStorageProp（只能传 string）
       卡片 --postCardAction(router|message|call)--> FormExtensionAbility / UIAbility
```

**能做**：文本、图片、`List`（纵向）、`Canvas` 自定义绘制（画折线/柱状/进度条）、属性动画与显式动画、点击按钮触发 router/message/call 三类事件、`setFormNextRefreshTime`（≥5 分钟）、定时/定点/多定点/网络条件刷新。
**不能做**：`Scroll` / `Grid` 组件、左右滑动的控件、`setTimeout`、native/so、HSP 动态包、卡内直接网络请求、卡内取 `getContext`、断点调试、热重载、极速预览。
**不要求**：应用进程常驻（卡片由系统服务托管）。
**配额**：每卡每天定时刷新 ≤50 次（0 点重置）；`setFormNextRefreshTime` ≥5 分钟；`updateDuration` 粒度 30 分钟；API 20+ 单次刷新数据 ≤10MB / ≤20 张图（API 19- 图片 ≤5 张、每张 ≤2MB）。

## 5. 四条路线对比

### 5.1 路线 a：全量鸿蒙移植（Flutter OHOS 分支）

| 维度 | 评估 |
|---|---|
| 前置条件 | DevEco Studio 5.0+ / command-line-tools 5.0+、OpenHarmony SDK API12、JDK17、ohpm/hvigor/node；Flutter 降到 3.35.7 或升到 3.41.9；华为开发者账号（真机签名需实名认证） |
| 主要工作 | ① Flutter SDK 换分支 + `flutter create --platforms ohos` 生成 `ohos/` 工程；② 47 个依赖逐个换 `git:` 引用并回归；③ `pdfrx` 换库或自写 ArkTS 插件；④ 全部原生通道（`android/app/src/main/kotlin/.../widget/` 那 6 个 Kotlin 文件 + `HomeWidgetBridge`）需重写成 ArkTS；⑤ 1425 例测试回归（golden、字体、平台分支） |
| 工作量 | **6–12 人月** |
| 风险 | **致命**：Flutter-ohos 产物最低 API 12，**装不进 HarmonyOS 4.2（API 8/9）设备**；即使升级设备也需再买/换手机 |
| 能达成 | 完整应用 + 服务卡片（ArkTS 卡片另写） |

**判定：对本机不可行。**

### 5.2 路线 b：只做鸿蒙「壳」应用，唯一职责是提供几张服务卡片

| 维度 | 评估 |
|---|---|
| 形态 | 独立 HAP（ArkTS/Stage），不做完整 UI，只实现 `EntryFormAbility` + 3~4 张卡片（电费 / 课程加权 / 数据一览 / 课表）；卡片自己拉数据 |
| **必须先解决的前置** | **工具链**：API 9 需 **DevEco Studio 3.1 Release**（2023/05/15，华为版本表已标 NA）；且本机 API 版本实测 8/9，能否装上需实测。**这是整条路线的生死线** |
| 需重写的东西 | ① **登录/CAS + MFA**：教务是 CAS 单点登录，`FormExtensionAbility` 只有 10 秒且无 UI，**无法在卡片侧完成登录** → 必须「主应用登录 → 把会话写进 `dataStorage`/`Preferences`/分布式 KV → FormExtensionAbility 读会话发请求」；② **HTTP 接口**：电费、成绩加权、数据一览、课表（当前 Dart 侧 `lib/features/home_widget/` 的 `home_widget_background.dart` 已经算好了同样的快照，逻辑要**用 ArkTS 重写一遍**）；③ **会话持久化**：Hive/`flutter_secure_storage` 换成 `@ohos.data.preferences` / `@ohos.data.relationalStore`；④ **GBK 解码**（教务响应是 GBK，Dart 用 `fast_gbk`，ArkTS 需自写或用 `util.TextDecoder` 指定 gbk）；⑤ **数据模型**：卡片只能通过 `LocalStorageProp` 收 **string**，与现有 `HomeWidgetSnapshot` JSON 快照口径天然吻合（可复用同一份 JSON 结构） |
| 卡片能显示什么 | 与安卓小部件等价：电费余额（主值 + 房间 + 更新时间）、课程加权（主值 + 专业排名）、数据一览（≤5 格）、今日课表（2×4 / 4×4 可放 4~6 行）；`Canvas` 可画折线/进度条；`List` 可做纵向课程列表 |
| 工作量 | **3–6 人周**（ArkTS 卡片 + 登录桥 + 4 个接口重写），**不含工具链攻关** |
| 风险 | ① API 9 工具链已停产、SDK 可能下架；② 本机 API 8/9 能否装 API 9 产物未验证；③ HarmonyOS 4.x 设备占比已归零（华为自己不再统计），投入产出比极低；④ 真机调试需华为开发者账号 + 实名认证 |
| 能达成 | 真正的「服务卡片」（微/小/中/大档、上滑图标呼出、堆叠/组合） |

**判定：技术上唯一能拿到「真服务卡片」的路，但前置风险极高，建议先花 0.5 人天做「工具链可行性验证」再决定。**

> **成本修正（2026-09-19，见 §2.6）**：华为官方博客《Flutter + 鸿蒙 | 服务卡片开发干货（一）》给出的做法是「Flutter 侧算好数据 → MethodChannel → ArkTS 写 SharedPreferences → `EntryFormAbility` 读并 `formProvider.updateForm`」，与本项目 Android 侧现有的 `HomeWidgetBridge`/`HomeWidgetStore` 同构 —— 于是本路线里「CAS 会话桥 + 4 个接口 + GBK 解码」**可以整块省掉**（数据准备留在已有 Dart 代码里），ArkTS 侧只剩卡片 UI + 读 KV；再若「独立 HAP 壳读公共目录 JSON」可行，则连会话都不需要。

### 5.3 路线 c：快应用 / 原子化服务卡片

| 子路线 | 评估 |
|---|---|
| 元服务卡片 | 与路线 b 完全同构（同样是 HAP + `FormExtensionAbility`），**受同样的 API 版本限制**；额外要满足元服务上架规范。无独立优势 |
| 快应用卡片 | 「卡片」是**嵌入超级 APP / 交互场景**的形态，打包在同一 RPK 内，通过 `manifest.json` 的 `widgets` 声明；能力是快应用页面的**子集**（不能用 `app.ux` 公共能力、不能引本地图片、不能用 `global` 存数据、不支持 `schema:internal://`）。门槛：华为开发者联盟注册 + 实名认证 + 快应用 IDE + AGC 创建快应用。**「快应用卡片能否出现在鸿蒙桌面『服务卡片』栏」未查到一手来源** |
| 工作量 | 快应用卡片：2–4 人周（如果桌面能展示才有意义）；元服务卡片：同 b |
| 风险 | 形态错配风险最大 —— 可能做完发现不在桌面上 |

### 5.4 路线 d：维持现状（安卓小部件）+ 在安卓 API 内做到「更像真卡片」

**现状（本项目已实现）**

| 项 | 现状 |
|---|---|
| 渲染 | `MetricWidgetRenderer.kt` 用 `RemoteViews`；24 个 receiver = 3 指标（dashboard / electricity / grades）× 8 档尺寸 |
| 布局 | `res/layout/home_widget_dashboard_*.xml`（8 档）+ `home_widget_metric_*.xml`（8 档） |
| 元数据 | `res/xml/home_widget_*_info.xml`：`minWidth/minHeight` = cells×70−30，`targetCellWidth/Height`（API 31+），`resizeMode="horizontal|vertical"`，**`updatePeriodMillis="1800000"`**（30 分钟，平台硬下限） |
| 后台刷新 | `WidgetRefreshScheduler.kt`：`JobScheduler` 周期任务 16 分钟（平台下限 15 分钟）+ `setPersisted(true)` 重启恢复；一次性任务（解锁 / 开 App）立即刷；`WidgetRefreshJobService.kt` 执行 |
| 数据 | Dart 侧算好 `HomeWidgetSnapshot`（label/value/unit/valueShort/sub1/sub2/state/message/updatedAt/accent/cells）→ 原生只渲染 |

**还能做什么（全部在 Android API 内，无需鸿蒙）**

| 增强项 | 可行性 | 说明 |
|---|---|---|
| **卡内按钮交互** | ✅ 可做 | `RemoteViews.setOnClickPendingIntent(viewId, pendingIntent)` 可让**任意子 View** 可点（「立即刷新」「切换指标」「直接进电费页」）；集合项内用 `setOnClickFillInIntent`。注意 Android 12+ 的 `PendingIntent` 必须显式 `FLAG_IMMUTABLE` |
| **更及时刷新** | ✅ 可做（有下限） | `updatePeriodMillis` **最小 30 分钟**（平台硬下限，设更小也无效）；`JobScheduler`/`WorkManager` 周期任务**最小 15 分钟**；一次性任务可由 `ACTION_USER_PRESENT`（解锁，需运行时注册）、App 启动、`ACTION_MY_PACKAGE_REPLACED`、网络变化等触发 —— **这就是「真卡片」刷新体验的天花板** |
| **内容更丰富** | ✅ 可做 | ① 图表：在 App/JobService 里用 `Canvas` 离屏画成 `Bitmap` → `setImageViewBitmap`；② 集合滚动：`RemoteViewsService` + `RemoteViewsFactory`（`ListView`/`GridView`）可做「今日课表 N 行」；③ 深色模式：`values-night/colors.xml`（项目已有）；④ 多尺寸自适应：`onAppWidgetOptionsChanged` + `AppWidgetManager.getAppWidgetOptions` 按实际尺寸换布局 |
| **进入桌面的入口** | ⚠️ 受限 | 华为桌面**不触发** `requestPinAppWidget` 的 PendingIntent 回调（项目已踩过坑，靠「已绑定实例数差值」判断），只能引导用户「双指捏合 → 窗口小工具」 |
| **真动画 / 卡内输入 / 卡内 WebView** | ❌ 做不到 | `RemoteViews` 只支持平台白名单里的布局与控件（`FrameLayout`/`LinearLayout`/`RelativeLayout`/`GridLayout`/`AnalogClock`/`Button`/`Chronometer`/`ImageButton`/`ImageView`/`ProgressBar`/`TextView`/`ViewFlipper`/`ListView`/`GridView`/`StackView`/`AdapterViewFlipper`/`ViewStub`），**不支持自定义 View、不支持 Compose、不支持 WebView**（来源：Android 平台 `RemoteViews` 机制，参考 [developer.android.com/…/appwidgets](https://developer.android.com/develop/ui/views/appwidgets/overview)；本条为平台既有行为，本次未逐句摘录原文） |
| **秒级/分钟级实时刷新** | ❌ 做不到 | 系统调度下限 15–30 分钟；Doze/省电策略下还会被推迟 |
| **鸿蒙桌面专属形态** | ❌ 做不到 | 「上滑应用图标呼出卡片」「堆叠卡片」「组合卡片」「微卡片」这些是**鸿蒙服务卡片框架**独有的桌面交互（启动器字符串实测），安卓小部件在「窗口小工具」栏，没有对应形态 |
| 精确闹钟 | ⚠️ 不建议 | Android 12+ 需 `SCHEDULE_EXACT_ALARM`，华为 ROM 上更可能被拒；且小部件刷新差几分钟无意义（项目已选 `inexactAllowWhileIdle` 口径） |

**工作量**：每项 1–3 人天（卡内按钮 + 课表集合列表是性价比最高的两项）。

## 6. 推荐落地路径与分阶段任务

### 6.1 推荐

> **主推路线 d（安卓小部件增强），把「鸿蒙服务卡片」列为「设备/环境升级后再评估」的长期项。**

理由：
1. 用户设备 HarmonyOS 4.2 的 HAP 运行时 API 版本只有 **8/9**，而当前唯一活跃的鸿蒙工具链（DevEco 5.x/6.x = API 12+）**产物装不进去**；能装的只有 API 9 的 DevEco Studio 3.1（2023 年，华为自己标注为 NA）。
2. 华为官方「存量设备 API 版本使用数量」表已**完全不统计 4.x/API 9 及以下**，这条设备线在生态上已出局。
3. 即使强行走通路线 b，收益与现状（「窗口小工具」里的小组件）**功能等价**：都是「桌面上显示电费/加权/一览数值」，差距只在桌面形态（上滑呼出 / 堆叠 / 组合 / 微卡片）与刷新机制。
4. 路线 d 的成本是「人天级」，且**不依赖任何华为账号、工具链、审核**。

### 6.2 建议的分阶段任务

**阶段 0（0.5 人天，纯决策）——「工具链可行性验证」，只做不承诺**
- [ ] 申请华为开发者账号并完成实名认证（服务卡片侧的绝对前置）
- [ ] 安装 DevEco Studio，用 `hdc shell param get const.ohos.apiversion` **确认本机 API 版本究竟是 8 还是 9**（`hw_sc.build.os.apiversion=8` 与 `persist.sys.ohc.apiversion=9` 冲突，必须定论）
- [ ] 确认 DevEco Studio 当前版本是否仍可把 `compatibleSdkVersion` 选到 ≤9（华为版本表只登记了 DevEco Studio 3.1 对应 API 9）
- [ ] 建一个空白 HAP 工程，把 `compatibleSdkVersion` 压到最低，**实测能否 `hdc install` 到 LIO-AN00**
- [ ] **决策门**：装不上 → 关闭鸿蒙路线；装上了 → 才进入阶段 1

**阶段 1（1–3 人天）——安卓小部件「像真卡片」，与鸿蒙无关，立即可以做**
- [ ] 卡内按钮：仪表盘卡加「立即刷新」「切换指标」，电费卡加「进电费页」，用 `PendingIntent`（`FLAG_IMMUTABLE`）+ `WidgetRefreshScheduler.refreshNow()`
- [ ] 课表集合列表：`RemoteViewsService` + `RemoteViewsFactory` 把「今日课表」做成 2×4 / 4×4 档可滚动列表
- [ ] 图表化：把「课程加权趋势 / 电费走势」用 `Canvas` 离屏画成 `Bitmap` → `setImageViewBitmap`
- [ ] `onAppWidgetOptionsChanged` 按实际尺寸换布局，而不是只靠 8 档固定 XML

**阶段 2（若阶段 0 通过，3–6 人周）——鸿蒙壳应用 + 服务卡片**
- [ ] 建 HAP 工程（ArkTS / Stage），`module.json5` 配 `FormExtensionAbility` + `form_config.json`（先做 2×2、2×4、4×4 三档，`isDefault` 只留 1 张）
- [ ] **登录桥**：主应用登录后把 CAS 会话/TGC 写进 `Preferences`，`EntryFormAbility` 读取
- [ ] **HTTP 层**：移植 `lib/features/home_widget/data/home_widget_background.dart` 的取数逻辑到 ArkTS（电费 / 成绩加权 / 数据一览 / 课表），含 GBK 解码
- [ ] **快照复用**：让 ArkTS 产出与 `HomeWidgetSnapshot` 完全同构的 JSON，卡片侧 `LocalStorageProp` 接收 → 两端数据口径不分叉
- [ ] 刷新策略：`updateDuration`（30 分钟的整数倍）+ `onFormEvent` 手动刷新 + 主应用 `reloadAllForms`（注意 API 22 起才有；API 9 用 `updateForm`）
- [ ] `Canvas` 画进度条/折线；`List` 做课表（**不要用 `Scroll` / `Grid`**）
- [ ] 签名 → `hdc install` 真机验证 → （可选）上架 AGC

**阶段 3（长期，等设备升级到 HarmonyOS NEXT 后再评估）**
- [ ] 用户换机到 HarmonyOS 5.0+ 后，路线 a 的「值不值」需要重新算：Flutter-ohos 主线 3.41.9/3.44.9 已可用，但本项目是 3.38.7，**升/降版 + 47 依赖 + `pdfrx` 替换**的账要重新做

### 6.4 主要风险点

| 风险 | 等级 | 说明 / 缓解 |
|---|---|---|
| **工具链断代** | 🔴 高 | HarmonyOS 4.2 的 HAP 运行时 API 只有 8/9，而现役 DevEco（5.x/6.x）最低 API 12。官方登记的 API 9 工具链是 2023 年的 DevEco Studio 3.1，华为可能已下架。缓解：阶段 0 先验证 |

| **审核与上架** | 🟡 低 | HAP 上架需 Release `.app` + 完整签名链；校园类应用上架还需资质（与是否鸿蒙无关） |
