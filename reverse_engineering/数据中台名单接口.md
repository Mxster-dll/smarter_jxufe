# 竹简数据中台「同侪名单」接口（学生个人数据中心 · 校内关系）

> 侦察日期：2026-09-19（真实会话，账号 2202500001）。目标：数据中心卡片上的「舍友 3 人 /
> 同班级 48 人 / 同年级 7905 人」如何点开看**名单**，并供 AA 算账「一键加舍友」使用。

## 1. 底座：组件接口是「组件绑定」的，请求体里的 `sql` 一律被忽略

宿主 `https://dzj.jxufe.edu.cn`，请求体与响应 `data` 均按 `DzjCrypto`（AES + `fixedSalt`）
加密，`Referer` 必须是 `https://dzj.jxufe.edu.cn/app/66eef481a9a3/82e98baafb40`。

| 端点 | 语义 | 实测 |
|---|---|---|
| `POST /api/app/component/data/get` | 取该组件**第 `index` 个指标**的**一行聚合值** | 同侪组件 index 0..4 → `{"sj":7905}` / `{"sj":48}` / `{"sj":201}` / `{"zs":3}` / `{"zs":0}` |
| `POST /api/app/component/data/search` | 取该组件**第 `index` 个指标的行集**（分页） | 同组件 index 0..4 → `{"pageInfo":[…],"total":7905/48/201/3/0}` |
| `POST /api/app/component/dve/getSql` | 聚合表达式（`_.yAxisInfoList[].sqlExpression`） | 网费卡用它取 `max(t_ry_wf.wfye)` |

- **`data` 里传的 `sql` 字段是装饰品**：拿消费组件（`u:66549841d896`）传
  `select * from t_xssj_bzks where …`，回的还是**消费明细**（`{"shmc":"浓汁烧",…}`）。
  `data/get` 传 `select 999 as sj` 回的也是真人数 → **两个端点都不认请求体 SQL**。
- `filterConfig`（两处都传 `[]`）**是认的**，形状见 `dve/getSql` 的 `filterInfoList`：
  `{'columnName':'','filterType':'sql','tableName':'','type':'VARCHAR2','values':[<SQL 谓词>]}`
  → 谓词被**原样拼进 WHERE**：`username = '同学己'` → total 1；`ssdw = '会计学院'` → total 1057。
  ⚠ **不能用 `#{U_用户名}` 占位**（→ `code=50000 系统异常`），只能用字面量；
  ⚠ 只能过滤该 index 行集**已暴露的列**（`userid`/`ssdz`/`ssbj` 直接报 50000）。

## 3. 会话（App 侧）

`DzjAuthRepository` 的链：`auth.hive` 的 `TGC|<账号>` → `GET https://ssl.jxufe.edu.cn/cas/login?service=https%3A%2F%2Fdzj.jxufe.edu.cn%2Fapp%2F66eef481a9a3`
（302 带 `ticket=ST-…`）→ 访问该 ticket 地址 → 响应 `Set-Cookie` 下发
`SESSION` / `fixedSalt` / `enableTransEncrypt` / `isLoggedIn` / `loginType`。
实测**离线可用**：把 `app_data/auth.hive` 复制到临时目录后，用 TGC 直接跑通整条链
（探针 `test/tmp_dzj_peers_probe.dart`，用完即删）。
⚠ 会话存活期短（实测两次探针之间即过期，`code=50002`）→ 业务仓库的
「失败 → `refreshSession` → 重试一次」是必需的。

**2026-10-01 · 会话过期代价实测 + 预检（重要）**：App 把会话落在 Hive 里且
**不看 TTL**（`dzj_auth_local_datasource.dart` 的 `getSession` 命中就用，
`getUpdatedAt` 至今无人调用）。真机那份会话已躺 **472 小时**，实测：
- 首屏那批（19 并发 + 5 个身份文本）**全部**回 `code=50002`，而 `_guard` 当时把
  异常吞成 null → 界面只有转圈、「在加载什么」完全不可见；
- 靠「全都空」猜出会话失效后整批重打：首屏 **6568ms**（冷连接），而同一批
  紧接着再跑只要 **537ms** → **慢的是白打一轮，不是 SQL**；
- 并发度本身不是瓶颈：死会话下 20 并发打 `manageTreeByVersion` 实测 64ms
  （N=1 冷连接 450ms），20 个真实业务请求 81ms。

因此现在改了两处：① `DzjApiRemoteDataSource.probeSession`（1 个轻请求 =
`manageTreeByVersion`，死会话 22ms 就回 50002）**先探后打**，死会话直接换、
不再白打一整轮；② `code=50002` 一律抛 `DzjSessionExpiredException`，
`_guard` **不再吞它**（普通业务失败仍照旧回 null）。换会话是**单飞**的
（`DzjAuthRepository.refreshSession` 按账户复用同一个 Future）—— 页面改成
各卡自己取数之后，5 个 provider 会同时发现会话死了，并发换票会互相作废
（统一认证的 ST 是一次性的）。

## 6. 「十个子页面」的发现方式（2026-09-20 打通 · 本轮 App 落地）

### 6.1 页面树：`manageTreeByVersion`（**唯一可靠出处**）

```
POST https://dzj.jxufe.edu.cn/api/page/manageTreeByVersion
body（AES 加密）= {"url":"66eef481a9a3", "accessFlag":1, "type":"web"}
→ {"tree":[{"menuName":"个人首页","pageKey":"82e98baafb40","menuType":"C"},
           {"menuName":"个人数据","pageKey":"c62ddfc1d7b4","menuType":"M",
            "children":[ …十个内容页… ]}]}
```

**入参怎么来的**：学校前端 `js_umi.c9aa3507.js` 里导出 `o6` 的函数体是

### 8.1 表格明细：`POST /api/app/component/data/dataList`（数据对象通道）

### 9.1 `filterConfig` 在「校内关系」组件上可用，且**认 `#{U_用户名}`**

先前（§6/§8）记的是「`filterConfig` 能用、但 `#{U_用户名}` 占位会 `50000 系统异常`」——
那只在**「相关人员」组件**（`u:af43933a919c`）上成立。在**「校内关系」组件**
（`u:fcd2d17a9131`）上实测两条都可用（`%TEMP%\dzjprobe\collegefilter.py` / `selffilter.py`）：

| 请求 | 结果 |
|---|---|
| `index=0`（同年级）无过滤 | `total=7905` |
| `+ filterConfig` `ssdw='计算机学院'` | `total=726` |
| `+ filterConfig` `ssdw=(select ssdw from t_xssj_bzks where userid=#{U_用户名})` | **`total=726`** ✓ |
| `+ filterConfig` `ssdw='计算机与人工智能学院'`（**本地学籍的叫法**） | `total=0` ⚠ |
| `+ filterConfig` `ykth='2202500001'`（本人） | `total=0` → **行集不含本人**（SQL 有 `userid != #{U_用户名}`） |
| `index=1`（同班）`+ ssbj='25计算机2班'` | `total=48` ✓（谓词在别的 index 上也灵） |

结论：
- **学院名不能用本地那一套拼**：学籍 XML 写「计算机与人工智能学院」、学工系统写「计算机学院」
  → 用子查询让**服务端**自己解析成本人学院，客户端一个中文字都不拼（也不需要账号字面量）。
- 谓词只能引用该维行集**已暴露的列**：`index=0` 的行有 `ykth/username/sznj/ssdw/sex`；
  换 `userid` 当列名直接 `50000 系统异常`。
- **`pageSize` 上限 = 500**（给 2000/8000 → `50000 分数数据量不能大于500`）；同年级 7905 行
  要自己翻页得 16 个请求，而 `total` 本来就是**过滤后**的总数 → 人数走
  `data/search` + `pageSize:1` 读 `total`，**一次请求**（App 侧 `fetchPeerCount`）。

⇒ App 侧把它做成一个**派生维度** `DzjPeerDimension.gradeCollege`（复用 `index=0` 的行集 +
`filterSql`），与五维并列在「校内关系」卡里，人数单独问一次；成绩页第三项的分母改读它
（实测 `726`，原来硬编码 `7902`）。

用户原话（两轮，第二轮是纠正）：

2. 「我的意思是这两个功能本身就很极高的相似度，那不如直接融合为一个功能。**所有的卡片统一样式**，
   然后**重复的卡片不重复显示**，**可以归并的信息就归并显示**」

→ 落法 = **① 两份名单融合成 8 个「关系目」**（一个关系只出现一次）**② 全页卡片走同一个外壳**
（标题行唯一实现 `dcCardHeader`）。

### 10.1 融合：10 个关系目（`DzjPeerRelation`）

两个组件（`u:fcd2d17a9131` 校内关系 / `u:af43933a919c` 相关人员）**看起来**是同一批关系的两份口径，
但只有一部分真正同义。按**同义**归并之后是 **10 目**：

| 关系目 | 主口径（行里带学号 / 班级 / 年级） | 另一份口径（只有姓名 / 学院） |
|---|---|---|
| 同年级 | `grade` | — |
| 同年级同学院 | `gradeCollege`（派生，单独一问） | — |
| 同班同学 | `class` | `relatedClass` |
| 同年级同专业 | `major` | — |
| 同专业同学 | — | `relatedMajor` |
| 舍友 | `dorm` | `relatedDorm` |
| 同学院同生日 | `college` | — |
| 同学院同学 | — | `relatedCollege` |
| 同天入校同学 | — | `enrollDay` |
| 同天生日同学 | — | `birthday` |

- ⚠⚠ **归并判据 = 同义，不是"看起来像"**（用户 2026-10-09 当面纠正：
  「你不能把"同年级同专业"与"同专业"归并，这是不同东西」）——
  - ✅ 同班 = 同班级（同一个班必然同一个年级，两套系统只是给的列不同）；
  - ✅ 舍友 = 同宿舍；
  - ❌ 「同年级同专业」= 同年级 **∧** 同专业（**子集**）≠「同专业同学」（**不限年级**）；
  - ❌ 「同学院同生日」同样多一个生日约束 ≠「同学院同学」。
  这两对**各占一目**；并起来会把一个子集的行集换成更大的行集，**数字直接偷换**。
  同理：这两目的主口径没数据时**就是不铺**，绝不用另一份的数顶替
  （回落只发生在同义的两对上）。守卫钉着这四条。
- **同义两对是「合并式」，不是「切换式」**（用户 2026-10-09：「同班和同宿舍，你不用做成
  切换式的，而是做成**信息归并式**的」+ 同日拍板「方格预取并显示合并后的真实人数」）：
  - 进页面就把**两份名单都取回来**（[dzjPeerMergedProvider]，两份**并发**）→
    `dzjPeerMerge` 按**学号**去重（两边都没学号才回落姓名）、**字段取并集**
    （学号/班级/年级来自校内关系，学院/性别来自相关人员）→
    方格上那个数 = **合并去重后的行数**，与点开的名单**永远一致**，弹层秒开；
  - 弹层里**一份名单**：没有来源胶囊、没有 ⇄；只在「相关人员」里收录的人带小标
    「仅『相关人员』名单收录」；副标题写「共 N 人 · 已合并：校内关系 X 行 · 相关人员 Y 行」，
    若某一份被分页截断（服务端计数 > 取回行数）再补「只列已取回的部分；服务端计数 …」
    （与「共 N 人 · 已列出前 M 人」同一口径：**数不一致就明说**）；
  - **代价（用户已知情选定）**：`dcRelationCard` 从 3 个请求变 7 个 —— 多出来的 4 个是这两对的
    两份名单（行集都小：同班几十行、舍友几行）；
  - 合并那一份还没到 → 方格画「… 人」（**不拿服务端计数冒充**）；合并失败 → 回落服务端计数
    并由卡片脚注交代「哪一份没取到」。
  - 两份口径是**两个组件、两条写死的 SQL**，即便同义人数也可能不一样（实测「同班」45 / 47）——
    所以合并后的人数与「服务端计数」本来就该有差，弹层里两个数都写着。
- 其余维度（只有一份名单的）照旧：数字 = 服务端计数，弹层「共 N 人 · 已列出前 M 人」；
  `DzjPeerEntry` 仍保留「主口径缺了回落同义的另一份」这条路（合并式下方格不直接用它，
  合并失败时才回落到它）。
- 铺排 = `DzjPeerEntry.build(...)`（domain 纯函数）：**按人数降序**、同人数保持目序
  （`List.sort` 不稳定，不兜底方格每次重建都换位置）；`-1` / 缺键 = 这一路没数据 → **整目不铺**；
  `0` 是**真·0 人**，照铺但灰显；`gradeCollege` 的 `0` 与「没拿到」一样不铺（口径同 2026-09-20 那轮）。
- 维度层（`DzjPeerDimension`）**不再自带配对** —— 配对是「界面上一格」的事，挂在关系目上；
  `relatedClass` 不是任何一目的 key（守卫钉着）。
- 四态（一张卡只有一份，判据看**两份**取数）：有目可铺 → 网格；某一份失败 → 网格照画 +
  **脚注如实说「那一份没取到：原因」**；两份都失败且无目 → 「读取失败：…」；还有一份在飞 →
  「正在读取…」；两份都到却一个目都没有 → 「暂无关系数据」。卡头**唯一**一枚「重新读取」
  （`Key('dzjPeerRetry')`）把三路一起重取（两份人数 + 派生维）；两张卡时代的
  `Key('dzjRelatedRetry')` 已删除（守卫断言不许复活）。

### 10.4 踩到的坑 / 纠正

- ⚠⚠ **最贵的一条 = 我自己先并错了**：第一版按"看起来像"把「同年级同专业↔同专业同学」
